Good to know

Three ideas worth understanding

These concepts explain how models work, how agents retain information and where execution risks can arise.

Memory is not training

An agent can store selected preferences and project details in persistent memory. Retrieval augmented generation (RAG) searches an external collection and adds relevant information to a request when needed. Skills provide reusable instructions for specific tasks.

These mechanisms help an agent access information across tasks and sessions, but they do not update the model’s learned weights. Training or fine tuning is a separate process.

Recall · Retrieval · Instructions

Model size and context

Parameters are learned numerical values, often called weights. Tokens are pieces of text processed by a model. Larger models can perform better on some tasks, but they generally require more memory and computing power.

Quantization stores model weights at lower numerical precision to reduce memory use. Its effect on quality depends on the model, quantization method and task. The context window limits how much input, conversation history, and generated output a model can process in a single request.

Longer context windows require additional memory for the key value (KV) cache. If memory becomes constrained, the runtime may need to offload data, reduce the available context, or run more slowly.

Parameters · Tokens · Quantization · Context

Control access and execution

Sandboxing limits where commands can run and which resources they can access. The principle of least privilege means an agent should receive only the access required for its task. Approval settings let you review sensitive actions.

Logs, tests and human review help catch mistakes. Containers add a layer of isolation, but their protection depends on their configuration, mounted folders, network access and the host system.

Memory planner

Estimate your memory budget

As a rough guide, 4 bit weights need about 0.5 GB per billion parameters and 16 bit weights about 2 GB, before overhead. The planner takes selected Ollama download sizes, multiplies them by 1.2, adds 2 GB for context and runtime, and compares the result with 70% of the memory you select. 02

Choose a model with tool support

Choose a model that supports the tool calling format expected by your agent runtime, provides enough context for your tasks and fits within your available memory.

Model families

Models worth knowing

Each family has different capabilities, sizes and licensing terms. Choose a specific model for your task, check its requirements and license, and test it with your own prompts and tools.

Is tool support relevant? Yes, for agents.

An agent can ask its runtime to call a named tool and provide the required arguments. The runtime then validates the request and executes the action. A model must support the tool calling format expected by the agent runtime and return valid arguments. Otherwise, the action may fail or produce an unusable result. In Ollama, you can filter the library by the tools tag and read its tool calling guide. Reliability varies by model, task, and runtime, so test the exact combination you plan to use.

Protect your workspace

Finally, secure, test and use

Containers add an isolation layer by running selected agent tools away from your files and system. They reduce risk but do not guarantee safety. Commands are for macOS, Linux and WSL2 on Windows.

01

Install Docker and create a workspace

Install Docker Desktop, or Docker Engine on Linux, and start it. Then create one dedicated folder. It is the only folder the agent tools should see.

Terminal · Verify Docker · macOS / Linux
docker --version
docker info
Terminal · Create shared workspace · macOS / Linux
mkdir -p "$HOME/AI_Workspace"
Choose the Docker installer for your system ↗
02

Turn on the Hermes Docker backend

Hermes runs its terminal, file and code tools inside a container. The application itself stays on your computer.

Terminal · Edit settings
hermes config edit

Merge these keys into the terminal: section of your profile configuration, usually ~/.hermes/config.yaml. Do not create a second terminal: key.

Hermes · Docker backend
terminal:
  backend: docker
  docker_mount_cwd_to_workspace: true
  docker_network: false
  docker_forward_env: []
  container_persistent: false
  • Network access is off for container commands, and no host environment variables are forwarded.
  • Each session gets a fresh container. CPU and memory limits use the Hermes defaults.
  • Open your AI_Workspace folder in Hermes, or start the CLI from it.
Terminal · Check Hermes configuration · CLI
hermes config check
02

Build a Goose tools image

Goose can run selected extensions inside a container. The application and your model provider stay on your computer.

Save this file as Dockerfile in an empty folder, then build it from that folder.

Dockerfile · Goose extension tools
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates curl bzip2 bash git python3 python3-venv nodejs npm && rm -rf /var/lib/apt/lists/*
RUN curl -fsSL https://github.com/aaif-goose/goose/releases/download/stable/download_cli.sh -o /tmp/install-goose.sh \
    && CONFIGURE=false bash /tmp/install-goose.sh \
    && install -m 0755 /root/.local/bin/goose /usr/local/bin/goose \
    && rm -f /tmp/install-goose.sh \
    && rm -rf /root/.local
ENV HOME=/tmp
WORKDIR /workspace
CMD ["sleep", "infinity"]
Terminal · Build image · macOS / Linux
docker build -t goose-tools:local .
03

Start the container and a Goose session

Start the container with limited permissions and no network, then connect the Goose CLI to it. Adjust the resource limits to what your computer can spare.

Terminal · Install Goose CLI · macOS / Linux
curl -fsSL https://github.com/aaif-goose/goose/releases/download/stable/download_cli.sh | CONFIGURE=false bash
Terminal · Start Goose tools container
WORKSPACE_DIR="$HOME/AI_Workspace"
CONTAINER_MEMORY="4g"
CONTAINER_CPUS="2"
CONTAINER_PIDS="256"
TMPFS_SIZE="512m"

docker run -d --name goose-tools --init \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --read-only --tmpfs "/tmp:rw,nosuid,nodev,size=${TMPFS_SIZE}" \
  --pids-limit "$CONTAINER_PIDS" --memory "$CONTAINER_MEMORY" --cpus "$CONTAINER_CPUS" \
  --user "$(id -u):$(id -g)" --env HOME=/tmp \
  --network none \
  --mount "type=bind,source=${WORKSPACE_DIR},target=/workspace" \
  --workdir /workspace goose-tools:local
Terminal · Goose CLI · macOS / Linux
goose session --container goose-tools
Terminal · Stop and remove container
docker rm -f goose-tools

Goose Desktop does not use this container automatically. The --container option belongs to the CLI workflow and isolates only the configured extensions.

Security limits: no container configuration guarantees protection. Never mount your home directory, browser profile, SSH folder, cloud credentials or the Docker socket. The agent can change or delete files in the mounted workspace, so keep backups.
Ready for a session

How to launch and use your agent

This section covers the everyday steps for starting your agent after installation and model setup. It does not repeat the download instructions.

Hermes Agent

The standard desktop setup uses a local model managed by Hermes. Once the model is installed, you can use Hermes through its graphical interface without running terminal commands.

1

Open Hermes Desktop from your Applications folder or system app launcher.

2

Open the model selector and choose the local model you set up earlier in Local Models.

3

Start a new conversation. Give Hermes access only to the tools and project folder needed for that task.

4

Review approval prompts before allowing file changes, terminal commands or other sensitive actions.

The Local Models option uses Hermes’ built in llama.cpp runtime and downloads models through the desktop interface. It does not install Ollama. To use an existing Ollama service with Hermes, configure it separately as a provider.

Goose with Ollama

Ollama serves the local model. Goose connects to that service and uses extensions to perform approved tasks.

1

Start the Ollama application or service. Confirm that the model you selected during setup is available.

2

Open Goose Desktop. In its model settings, choose Ollama as the provider and select the model already downloaded.

3

Before enabling extensions, open Settings → Chat → Default Mode and choose Manual Approval or Smart Approval. Autonomous mode is the default. Changing the default affects new sessions only, so check the mode of the session you are using.

4

Enable only the extensions required for the task. Check their commands and access permissions before use.

To run configured extensions in the Docker container through the separate CLI workflow, start a session with goose session --container goose-tools. This does not place the entire Goose Desktop app inside Docker.
